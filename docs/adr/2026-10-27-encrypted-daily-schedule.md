# ADR: Public リポジトリで今日の一問の先の出題を暗号化して持つ

## 背景と課題

2026-10-27 にリポジトリを Public にした（GitHub Actions を動かすため）。`src/daily/schedule.json` には先の日付の出題が平文で入っており、プレゼント抽選は正解を送ると応募できるため、先の答えが読めると遊ばずに当選を狙える。計画スクリプト `scripts/daily/plan.ts` も日付だけを種にしていたので、公開されたコードを実行すれば今後の出題を再現できた。Actions のログ（計画時に答えを出力していた）も公開される。

## 選択肢

1. 出題表を Private リポジトリに移し、デプロイと計画のときに読み書きする。
2. 出題表を暗号化して今のリポジトリに置き、鍵を Actions secret に置く。
3. 出題表を Supabase の表に置く。

## 決定と理由

2を採用する（ユーザーの選択）。リポジトリが増えず、既存のワークフローの形を保てる。

- 公開済みの日（2026-10-27 まで）は `schedule.json` に平文で残す。テストはこれだけで動く。
- 先の日は `src/daily/schedule.upcoming.enc` に AES-256-GCM で暗号化して置く。鍵は `DAILY_SCHEDULE_KEY`（32バイト、base64）。
- 計画の乱数の種は `HMAC-SHA256(鍵, 日付)` にし、鍵が無いと出題を再現できないようにする。計画のログは日付だけにする。
- 公開とテストは鍵が無いと公開済みの日だけを読む。公開（`daily:publish`）と計画（`daily:plan`）は、暗号化された日があるのに鍵が無ければ止まる。
- Public 化で読めるようになった 2026-10-28〜11-08 の12問は破棄して計画し直し、今後も選ばない（`plan.ts` の `LEAKED`）。

## 利点と欠点

- 利点: Private リポジトリやトークンの管理が増えない。出題の検証は CI（鍵あり）で続けられる。
- 欠点: 計画 PR の差分が読めないので、トリビアを PR 上で書き足せない（`npm run daily:schedule -- open` / `close` を使う）。鍵を失うと先の出題を読めず、計画し直しになる。鍵が漏れたら鍵を替え、先の出題を計画し直す必要がある。Git の履歴には 11-08 までの旧出題表が残る（破棄済み）。

## 見直し条件

トリビアの手入力が多くなった場合や、出題表を人が頻繁に直す場合は、Private リポジトリ（選択肢1）へ移す。
