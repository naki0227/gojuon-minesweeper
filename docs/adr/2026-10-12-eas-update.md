# ADR: EAS Update で JavaScript の変更を審査なしで配る

## 背景と課題

画面・ルール・文言だけの変更でも、毎回 App Store の審査を通す必要があった。オンライン対戦はサーバーと組み合わせて動くため、修正を早く配れないと旧版との不整合が長く残る。

## 選択肢

1. これまでどおり毎回審査に出す。
2. EAS Update（`expo-updates`）で JavaScript とアセットを配る。
3. 画面やルールをサーバーから取得する作りに変える。大きな作り直しになる。

## 決定と理由

2を採用する。Expo の標準機能で、既存の EAS ビルドと同じプロジェクトで使える。`runtimeVersion` は `appVersion` 方式にした。`fingerprint` 方式は AdMob のアプリ ID など、ビルド環境と更新を出す環境で値が変わる設定まで含めて計算するため、更新が届かなくなる。配信は手動のワークフロー（「EAS Update」）で行い、マージで自動配信はしない。

## 利点と欠点

- 利点: JS だけの修正を審査なしで配れる。ダッシュボードから前の版に戻せる。
- 欠点: ネイティブを変えたときにストアバージョンを上げ忘れると、古いネイティブに新しい JS が届く。EAS の無料枠を超えると費用がかかる。更新は次回起動から反映される。

## 見直し条件

ネイティブ変更の上げ忘れが起きた場合や、Android を配る場合は、`fingerprint` 方式とビルド環境の揃え方を再検討する。
